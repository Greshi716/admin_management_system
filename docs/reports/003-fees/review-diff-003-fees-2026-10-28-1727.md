## Should fix

**S1. The race path on the first brought-forward save is wrong and untested.**
- Location: `management/src/main/java/com/admin/management/fees/BroughtForwardService.java:62-69`
- Problem: `DataIntegrityViolationException` is caught inside the same `@Transactional` method, and then `current(studentId)` reads again through the same session. After a failed flush, PostgreSQL has aborted the transaction and the Hibernate session cannot be trusted. `findById` will most likely return the caller's own unsaved entity from the first-level cache, or fail with "current transaction is aborted". In both cases the "latest value" sent back as `STALE_VERSION` is wrong. The same catch also turns a numeric overflow (SQLState 22003, which Spring also maps to `DataIntegrityViolationException`) into a false "someone else saved it" message. No test covers this path. I am fairly confident about this but have not run it.
- Fix: catch only a unique/PK violation, and return `STALE_VERSION` without re-reading (or read in a new transaction). Add a test with two concurrent first saves.

**S2. Amounts above `NUMERIC(12,2)` are not refused beside the field (FR-011).**
- Location: `management/src/main/java/com/admin/management/fees/FeeStructureService.java:261-268` (`moneyError`) and `BroughtForwardService.java:106-121` (`validate`).
- Problem: there is no upper bound. Take 10,000,000,000.00 as an example. On a fee row it reaches the database and comes back as the generic 409 "The change conflicts with existing data." with no field error (`ApiExceptionHandler.fromCause`, default branch). On a first brought-forward save it comes back as `STALE_VERSION` (see S1). FR-011 and US1 scenario 6 say an invalid amount is "refused beside the field". `FeeSchemaIT` tests the overflow only at SQL level.
- Fix: add a field error 422 when `amount.precision() - amount.scale() > 10`, in both validators. Add an API test for each.

**S3. T030 is ticked although the owner check is not done.**
- Location: `specs/003-fees/tasks.md:129`, changed to `[X]` in commit `d80a3d4` ("feature 3 task").
- Problem: `specs/003-fees/quickstart-results.md:41` and `:53-55` still say "Open, owner task T030" and "Not done yet". SC-001 has no result. The task list now says something the evidence does not support.
- Fix: either untick T030, or have the owner do the timed check and record the time and pass/fail in `quickstart-results.md`.

**S4. The export has a "Fee state" column while the owner decision is still open.**
- Location: `management/src/main/java/com/admin/management/students/StudentTable.java:81-83` (hidden `feeState` column in the export), `specs/003-fees/tasks.md:149`, `quickstart-results.md:42`.

**M4. Concurrent first-row saves get the wrong message.** `FeeStructureService.java:167-185`: when a year has no status row yet, `lockForUpdate` locks nothing. Two windows saving the first row at once both insert `fee_year_status`, and the second gets the generic "This value already exists." instead of `STALE_VERSION`. With one admin this is unlikely. Fix: map `pk_fee_year_status` to `STALE_VERSION`, or insert the status row with `ON CONFLICT DO NOTHING` and then lock it.
